# 公開リポジトリ用ソースの作成

現在の開発リポジトリには、過去のコミット作成者・コミッターの個人用メールアドレスが残っています。ファイルを直したり現在のGit設定を変更したりしても、過去のコミットからは消えません。開発用の履歴を保持する場合は、次の手順で公開用ソースを別フォルダーに作成します。

この手順は既存リポジトリの履歴や公開設定を変更しません。公開先の作成・アップロードは別途行います。

## 内容の検査

Node.jsを使い、リポジトリのルートで実行します。

```powershell
node scripts/check-public-data.mjs
node scripts/check-public-data.mjs --history
```

検査対象は、Git追跡ファイルと、ignore対象ではない未追跡ファイルです。削除済みのファイルや、`node_modules`・`.env`・ローカルDB・資格情報・生成物などのignore対象は読み込みません。履歴検査では全ブランチ・タグから到達できるコミットのファイルと作成者情報も確認します。

結果にはファイル名、検出種別、件数だけを出力します。秘密値やメールアドレスそのものは出力しません。秘密鍵、既知のトークン形式、JWT、個人のホームディレクトリ、私用メール、現在のOSユーザー名を検査します。会社名や会社の公開Webサイトは残します。公開依存パッケージのlockfileに含まれる第三者の連絡先、架空のテスト用メール・ユーザー名は対象外です。URLのuserinfoをメールアドレスと誤認しないように区別します。Geminiの漏洩防止テストにある固定ダミー1件のみ、ファイル名とSHA256の両方が一致する場合に明示的に許可しています。

第三者OSSのライセンス原文には、保持が必要な著作権者の連絡先が含まれる場合があります。`THIRD_PARTY_NOTICES.txt`とそのWeb配信用コピーでは、生成されたライセンスブロックのSHA256が一致する範囲内だけ、メール表記を正規の帰属表記として扱います。別途固定保存した原文も、許可したファイル名とSHA256が一致する場合に限り同様に扱います。文書外のメール、トークン・秘密鍵、個人パス、現在のOSユーザー名の検査は継続します。ライセンス原文そのものをマスク・改変する処理ではありません。

パターン検査ですべての秘密情報を検出できるわけではありません。実アカウントのスクリーンショット、使用履歴の書き出し、設定のバックアップを公開フォルダーに追加しないでください。ソース以外の配布ファイルにも別途検査が必要です。

## 新しい公開用フォルダーを作る

```powershell
node scripts/export-public.mjs --destination .public-release/RunMeter --init
```

出力先はまだ存在しないフォルダーを明示します。同名フォルダーがある場合は停止し、上書きや削除は行いません。ソースは現在の作業ツリーから収集するため、未コミットの修正も含まれます。通常の未追跡ファイルも含まれるので、検査前に公開対象を確認してください。

`.git`やignore対象はコピーしません。シンボリックリンク、Windowsのジャンクション、リポジトリ外へ出るソースパス、既存の出力先を拒否します。内容の検査に問題がある場合、出力先を作る前に停止します。途中でディスク等のエラーが発生した場合には、新しく作った出力先が途中まで残ることがあります。再実行には別の未存在フォルダーを指定してください。

`--init`を付けると、公開用フォルダー内にのみ新しいGitリポジトリを作り、単一の初回コミットを作成します。作成者・コミッターには `RunMeter contributors` と `noreply@example.invalid` を使用します。これは架空の公開用アドレスであり、個人や会社の実在するメールアドレスではありません。このフォルダーのローカルGit設定にも同じ作成者情報と署名なしを保存し、以後のコミットで個人用設定を継承しないようにします。元の履歴、remote、hooks、Git署名設定は引き継がず、グローバルなGit設定も変更しません。`--init`を省くとGit履歴のないソースフォルダーだけを作ります。

公開用フォルダーで再検査してください。

```powershell
Set-Location .public-release/RunMeter
node scripts/check-public-data.mjs --history
git status --short
git log --oneline
```

ファイル内容を更新した場合は、別名の新しい公開用フォルダーを作り直し、検査と通常のビルド・テストを再実行してください。元の開発履歴をそのまま公開したい場合は、過去の作成者情報を公開してよいか別途判断し、必要な場合のみ履歴修正の手順を決めてください。

## 今後の取り扱い

- 実アカウントの認証情報・利用データは、アプリの端末内保存先に置きます。
- Gitへ追加する前に `git status --short` と公開データ検査を確認します。
- パブリック化後のコミットにも私用メールを残さないよう、公開用フォルダーのGit作成者設定を確認します。
- 秘密情報がすでに外部へ公開された場合、ファイルを消すだけで済ませず、該当するトークン・鍵を失効・再発行します。
